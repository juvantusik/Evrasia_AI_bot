# Evrasia AI Bot — обязательные антиошибки и правила выполнения работ

**Статус: обязательная инструкция для всех следующих чатов и изменений проекта.** Обновлено 2026-10-18. При противоречии техническим предположениям фактическое состояние production и актуальный код имеют приоритет.

## 1. Цель и запрет на имитацию прогресса

- Главная задача: рабочее API V5 для «СамЗаберу» на реальном Bitrix: логин/пароль → нативный TOTP (если подключён), иначе серверно подтверждённое доверенное устройство, иначе SMS только на проверенный номер из учётной записи; после защищённого входа показ бонусного PIN без повторной SMS.
- Прекратить бесконечные циклы «изучить → создать тестовую обёртку → написать отчёт → сказать “дальше”». Один законченный пользовательский сценарий приоритетнее десятков вспомогательных файлов.
- Не создавать параллельный слой SMS, JWT, trust или challenge, пока не проверена существующая основная реализация. Устаревшие экспериментальные V5Sms* классы не подключать к production; при несовместимости с каноническим V5LoginWorkflow использовать только основной механизм.
- Не считать количество коммитов, абстракций, тестов и документационных страниц показателем готовности. Каждый шаг должен иметь проверяемый результат, приближающий включение функции.
- Не повторять давно известные исследования. Сначала читать текущий код, последние решения, результаты сервера, затем выполнять нужное изменение.

## 2. Чего НЕЛЬЗЯ утверждать

- Не писать «проверено на Bitrix», если использованы только GitHub, синтетические PDO и mock-порты. Результат отмечать как SOURCE / SYNTHETIC / CI / REAL_MYSQL / REAL_BITRIX / HTTP_E2E.
- Добавление теста в workflow не означает его успешного выполнения. Отсутствие GitHub Actions runs/statuses означает **CI_NOT_CONFIRMED**, а не PASS.
- `php -l` подтверждает только синтаксис PHP; не означает корректность SQL, подключения, авторизации и бизнес-логики.
- Нельзя писать `FINAL_STATUS=PASS`, когда HTTP-запросы завершились `CURL_RC!=0`, даже если файлы существуют.
- Нельзя объявлять отправку SMS успешной после записи в outbox. Различать queued, provider sent, delivered (только если провайдер это подтверждает).
- Не описывать V5 как готовый, пока не работает реальный поток с Bitrix и серверными проверками безопасности.
- Не приписывать задержкам разработки весь ущерб по SMS без сверки финансовой аналитики. Но считать снижение SMS-расходов бизнес-приоритетом.

## 3. Как НЕЛЬЗЯ писать серверные copy-paste скрипты

- Не выдавать длинную пачку команд, требующую ручного редактирования. Один вставляемый wrapper с heredoc: создаёт временный файл, `bash -n`, запускает, выводит итог, удаляет файл.
- Не маскировать сбой команд через `|| true`, `grep ... || true`, перенаправление ошибок в `/dev/null`, либо смешивание частичных ошибок с итоговым PASS. Если операция необязательна, писать отдельный `SKIP/WARN`, не подтверждая её успешность.
- Не терять реальный код завершения из-за `set -e`, `&&`, командных подстановок или завершающего `echo`. Сохранять результат исполнения; `WRAPPER_RC` и `FINAL_RC` должны отражать сбой. Даже при падении скрипта должен печататься итог (например, через EXIT trap).
- Не ставить `EXPECTED_HOST` наугад: заранее проверять `hostname`, права, пути, назначение машины. Stop-before-write при несовпадении.
- Не использовать `127.0.0.1:80/443` без проверки адресов прослушивания. На production `evrasia` web слушал `192.168.103.141:80,443`; прошлые `curl --resolve ...127.0.0.1` завершились `RC=7`. Проверять `ss -ltn`, SNI/Host, маршрутизацию. Не приравнивать transport error к HTTP 503.
- Не использовать `curl -k` для передачи логинов, токенов и иных секретов. Для диагностики без credentials возможно отдельное явно обозначенное использование, но штатный TLS должен проверяться.
- Не включать в вывод пароли, токены, SMS-коды, cookie, заголовки Authorization, private keys, значения `.settings.php` и персональные данные.
- Не склеивать SQL-строки не проверив пробелы: ранее в `V5MySqlChallengeConsumption` образовался `UPDATE ev_v5_auth_challengesSET`. Проверять реальный сформированный SQL и исполнять тесты до коммита.
- Не печатать секреты и содержимое защищённых файлов при ошибках; вместо них `PRESENT=YES/NO`, хеши, маскированные признаки.
- Не делать произвольных `rm -rf`, DB UPDATE/DELETE, остановки Docker, изменения live PHP или nginx на production без проверки цели, backup и rollback.

## 4. Обязательный шаблон безопасного выполнения

Каждый диагностический блок должен:
1. Печатать `=== 1. HOST / ENVIRONMENT ===`, `MODE=READ_ONLY/WRITE`, `DATABASE_WRITE=NO/YES`, `API_WRITE=NO/YES`, `SECRETS_PRINTED=NO`.
2. Проверять hostname, root/права, путь Bitrix, проверяемые зависимости и прослушиваемые IP до любых действий.
3. До запуска проверять `bash -n`; для PHP — `php -l`; для SQL — реальное форматирование и параметры.
4. Проводить одну логическую операцию с отчётом `=== 2. CHECKS ===`, `=== 3. ACTION ===`, `=== 4. VERIFY ===`, `=== 5. RESULT ===`.
5. Подсчитывать `PASS_COUNT`, `FAIL_COUNT`; **любая обязательная ошибка = `FINAL_STATUS=FAIL` и ненулевой `FINAL_RC`**. Локальная успешная проверка не исправляет другой сбой.
6. Не завершать SSH-сессию и позволять скопировать весь безопасный вывод без ручных обрезок.
7. Перед WRITE в production: guards → исследование схемы/состояния → backup → проверка backup → минимальное изменение → функциональная проверка → план rollback. Для ошибок — остановка, а не продолжение по инерции.

## 5. Bitrix, SMS, production

- Bitrix production `evrasia.spb.ru`, docroot `/home/site_evrasia/web/evrasia.spb.ru/public_html`, host `evrasia`. Факт наличия `api/v5/router.php` и PHP lint не означает, что native V5 сервисы подключены. Истинное состояние получать с сервера, сравнивать SHA/git-версию и проверять HTTP на реально слушающем IP.
- V4 в production остаётся работающим; не заменять маршруты, регистрацию, 2FA и бонусы V4 при создании V5. V5 остаётся OFF/503, пока не выполнены критерии включения.
- Не считать номер телефона проверенным по `PERSONAL_PHONE` или клиентскому JSON. Нужна авторитетная версия подтверждения из Bitrix, проверенная на той же актуальной учётной записи.
- Нативный TOTP имеет приоритет; наличие MFA не должно быть поводом для downgrade на SMS. Trust только с серверной сильной проверкой, а не по флагу клиента.
- Одноразовые коды, лимиты SMS по пользователю/IP/устройству и затратам, защита от платного спама и блокировка повторного использования — обязательные требования, проверяемые на фактическом сценарии.
- Не считать `inTransaction()` доказательством непрерывности transaction: native код может выполнить COMMIT+BEGIN. Требуются согласованная транзакционная модель, реальные SQL-проверки и подтверждение на Bitrix.
- Никаких реальных отправок SMS, тестового списания бонусов или изменения пользователей без отдельного согласованного испытания с ограниченным бюджетом и тестовыми аккаунтами.

## 6. Как НЕ тратить ещё одну неделю

- После каждого вывода сервера сначала анализировать его и выбирать **непосредственно следующий необходимый рабочий шаг**, а не создавать очередную диагностическую экспедицию.
- Если препятствие — подключение Bitrix, решать подключение; если HTTP — адрес/маршрут; если native порт — конкретную реализацию; если SMS-provider — конкретную интеграцию. Не отвлекаться на независимые новые подсистемы.
- Сразу тестировать в соответствующем настоящем окружении безопасным способом: HTTP GET без credentials → Bitrix bootstrap/read-only → проверенные тестовые аккаунты → SMS с лимитом → login/session/PIN. Не выдавать тестовый стенд или mock за production E2E.
- Документацию проекта обновлять **в GitHub**, а не создавать отдельный Word-файл, если задача — закрепить правила для следующих чатов.
- На каждый результат писать: что реально изменено, где, фактический запуск и его статус, что осталось незавершённым. Если нет доказательства PASS, честно писать NOT_TESTED.
