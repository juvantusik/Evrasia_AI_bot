# Евразия: открытие добровольного TOTP 2FA для всех пользователей сайта

**Решение пользователя от 24.10.2026:** после успешно завершённого пилота разрешено предложить существующую штатную Bitrix TOTP 2FA всем пользователям личного кабинета сайта. Цель — пользователи, успешно вошедшие с защищённой сессией TOTP, самостоятельно просматривают реальный RestIS PIN списания бонусов без повторного VK/SMS.

**STATUS: BUSINESS_DECISION_APPROVED, PRODUCTION_PUBLIC_ROLLOUT_NOT_YET_DEPLOYED.** Этот документ фиксирует новое решение, не удостоверяет факт изменений production.

## Исходное подтверждённое состояние

- На production Bitrix сайт уже имеет глобально включённую OTP в **необязательном** режиме с сентября; пилотная веб-2FA с SMS-before-QR, нативной Bitrix TOTP-проверкой на входе, отключением и отзывом старых сессий работала на `USER_ID=880339`.
- 17.10.2026 оператор проверил настоящий вход `LoginByOtp()` с `Context::getUserId()` пользователя и `Context::isOtpUsed() === true`; `local/php_interface/pincode.php` показал реальный бонусный PIN непосредственно в личном кабинете, **без SMS**. Cookie-restored/старые сессии без `isOtpUsed` не могли получить PIN напрямую.
- Веб-компонент на production: `local/components/eurasia/totp.enrollment/class.php`. Пилотный код: `PILOT_USER_ID=880339`, методы `requirePilotUser()` и `requirePilotUserForDisable()`; последняя известная SHA 17.10.2026: `27de8a0d74b1613672740b2899afcc7a333b2f8e40557f5095fd98ad9ee6608e` — **исторический SHA, проверять текущий перед любым изменением**.
- Веб PIN: `local/php_interface/pincode.php`; ранее подтверждённая текущая сеансовая проверка: `$context->getUserId() === $userId && $context->isOtpUsed()`. PIN берётся из `CRestis::pincode`, но не должен разглашаться при одном только `b_sec_user.ACTIVE=Y`.
- Живые source-файлы website (`totp.enrollment`, account template, signin, pincode) хранятся на Bitrix production host, не в package `site-integration/samzaberu-v5/src`; этот GitHub feature-документ не может удостоверить их актуальные хэши/контент.

## Требуемое изменение сайта

1. Убрать **только pilot USER_ID allowlist** у доступности UI, enrollment и disable; оставить проверку сессии, текущего владельца аккаунта, Bitrix security module и полностью существующую штатную верификацию TOTP. Не менять core `Otp.php` или `TotpAlgorithm.php`.
2. Сохранить SMS-подтверждение подтверждённого телефона ПЕРЕД выдачей QR/secret, CSRF, одноразовую сессию подтверждения, время жизни/попытки и безопасный отзыв pre-MFA web/mobile sessions. До открытия всем убедиться в rate limits **per-account, per-IP и глобальном бюджете платных SMS**: прежние злоупотребления SMS не должны повториться.
3. Сохранить Bitrix MFA **OPTIONAL**. Для сайта приоритет: текущий действительно доверенный браузер (серверная проверка по аккаунту/устройству) → без нового TOTP/SMS; иначе активированный TOTP → TOTP; иначе SMS challenge после проверки пароля. Не принимать неподтверждённый идентификатор устройства за траст.
4. Прямой PIN доступен при текущей авторизованной веб-сессии и **ЛЮБОМ действующем server-verified Trusted Device**, в том числе созданном ранее по паролю, без дополнительного SMS/TOTP/MFA-upgrade. Если траста нет, прямой PIN доступен после пройденного TOTP либо нового SMS challenge с серверно доказанной session assurance; прежние cookie без действующего траста и без подтверждённого второго шага не годятся. Не принимать один флаг b_sec_user.ACTIVE или вход по паролю за доказательство.
5. Не менять мобильные контроллеры V4, JWT, trust, SMS API и сайт по домену. Но до общего открытия проверить, как **активированная Bitrix OTP влияет на `V4\Auth::signin` / `CUser->Login`** для конкретного аккаунта: изменение штатного глобального MFA для новых аккаунтов не должно незаметно ломать V4 клиентов. СамЗаберу V5 AUTH остаётся OFF / HTTP503.
6. Проверить UI desktop/mobile, подключение, неверные SMS/TOTP, отключение, отзыв прежних сеансов, PIN без SMS после свежего OTP, невозможность прямого PIN на прежней сессии, отсутствие лишних платных SMS. Приёмка на подготовленных реальных тестовых аккаунтах до публикации UI всем; не требовать новую VM и не переписывать проверенный пилот.

## Утверждение расширенного веб-MFA — 24.10.2026

**Новое явно одобренное пользователем production-направление:**

Нет траста и TOTP → до подтверждения SMS не выдавать PIN. SMS не используется как обход активного TOTP на незнакомом устройстве.

Не требовать отдельного MFA upgrade, в том числе у браузеров, которым доверие было присвоено после парольного входа. Проверять на сервере статус, пользователя, устройство, срок действия и отзыв trust; одного присланного device_id недостаточно.
4. После свежего TOTP или SMS challenge — защищённая web session, PIN RestIS можно показать без повторной платной SMS. **При действующем server-verified trust PIN показывается сразу и без дополнительной MFA, независимо от исторического метода регистрации траста.** Наличие произвольной cookie или записи OTP само по себе не является авторизацией PIN.

## Окончательное уточнение: действующий Trusted Device даёт PIN без SMS

**Прямое решение пользователя после обсуждения накопленных 44 210 Trusted Device (24.10.2026). Это правило заменяет все более ранние предположения данного документа о необходимости предварительного "сильного" MFA для уже существующего сайта/trust.**

- Для уже авторизованной веб-сессии, если сервер подтверждает **действующее доверие к текущему устройству для текущего USER_ID**, возвращать реальный PIN списания непосредственно в ЛК **БЕЗ SMS, БЕЗ нового TOTP, БЕЗ повторной или дополнительной MFA**. Это касается также трастов, ранее зарегистрированных по одному паролю (AUTH_PASSWORD). Нельзя искусственно разделять их на "старые", "новые", "сильные" для права на PIN.
- **Ничего не удалять или массово переоформлять в ev_trusted_devices.** 44 210 — сообщённый пользователем текущий масштаб накопленной базы; число не доказано в этом коммите как объём именно активных browser trust. Статус каждой записи проверяется непосредственно перед предоставлением доступа.
- Если текущего валидного траста нет и аккаунт с активным TOTP — проверка TOTP, затем PIN без SMS. Если траста и TOTP нет — единственный SMS challenge после успешного пароля, затем PIN без повторной SMS в подтверждённой сессии.
- При проверке trust обязательно подтверждать USER_ID, реальную серверную верификацию токена, состояние/отзыв/expiry и соответствие устройству; просто существование записи в БД или предъявленный device_id не являются валидным трастом. Не делать PIN доступным по одному паролю без валидного trust или второго фактора.
- **Техническое последствие:** существующая pilot-only ветка pincode.php в некоторых случаях требует AuthAssuranceService::hasPersistentCurrentAssurance *в дополнение* к hasValidCurrentTrust. Для общесайтового rollout это требование нужно снять для действительно валидного existing trust, но не убирать остальные проверки USER_ID, активного login, CSRF/Host, trust-server-validation. Входная pilot-only логика SMS/trust должна быть расширена на всех пользователей с сохранением антиспам-бюджета. Историческую website pilot TOTP проверку не переписывать.
- Это явный tradeoff: при компрометации реально доверенного устройства или его доверительного токена злоумышленник потенциально получает право на PIN без дополнительной SMS. Это допущение принято для сохранения экономии SMS на массовой накопленной базе.
- **Статус:** WEBSITE_BUSINESS_POLICY=APPROVED; WEBSITE_ROLLOUT=NOT_DEPLOYED; PRODUCTION_V4=UNCHANGED; V5_AUTH=OFF. Никаких production изменений данным коммитом. Раздельные V5-native epoch/mfa guards остаются отдельной инженерной работой; не объявлять их автоматически изменёнными через решение о website PIN.
