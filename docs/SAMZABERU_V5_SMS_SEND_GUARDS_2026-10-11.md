# СамЗаберу API V5 — защита SMS от спама и затрат

**2026-10-11.** Статус: **GitHub-only / OFFLINE TESTED / НЕ РАЗВЁРНУТО**.
Первоисточники: [реестр структур](STRUCTURE_REGISTRY.md), [контракт V5](SAMZABERU_API_V5_AUTH_CONTRACT_2026-10-11.md), [интеграционный README](../site-integration/samzaberu-v5/README.md).

## 1. Бизнес-логика (уже принято)

После подтверждения пароля:
- При действующем нативном Bitrix TOTP требовать TOTP, не обходить его даже сильным Trusted Device.
- Если TOTP достоверно отсутствует, и есть действующий Trusted Device, прошедший **сильную** регистрацию, завершить вход без SMS; старый V4 password-only trust недостаточен.
- В остальных разрешённых случаях показывать **только ввод SMS-кода**. Не запрашивать номер у пользователя — брать **серверный подтверждённый телефон аккаунта**.
- Только после подтверждённого второго фактора выдавать независимую V5 assured-сессию. Бонусный PIN показывать в такой сессии без дополнительного SMS.

До готовности реализации `api/v5/router.php` отвечает HTTP 503.

## 2. Что действительно написано и протестировано

`site-integration/samzaberu-v5/src/V5SmsDispatchBudget.php`:

- `V5VerifiedSmsDestinationPort` обязан возвращать авторитетно подтверждённый E.164 телефон, user ID и непрозрачную версию подтверждения. **Нет поля телефона в HTTP-запросе**, и нет продакшен-реализации источника пока.
- `V5SmsPriceCeilingPort` должен возвращать гарантированную **максимальную** тарификацию одного сообщения в младших единицах валюты. При отсутствии тарифа/несовпадении валют — отказ. Цифры и RUB в тестах **искусственные**, тариф провайдера не проверен.
- `V5SmsDispatchBudget` формирует 10 независимых HMAC-SHA256 окон с фиксированными областями ограничения, резервируя по 1 единице на каждый счётчик отправок и по верхней цене на глобальный бюджет стоимости.
- `V5AtomicSmsOutboxPort` — обязательный будущий **атомарный** интерфейс. Никакая реальная очередь, шлюз или SQL-интеграция пока не реализованы.
- `V5SmsQueuedDelivery` подтверждает лишь *постановку в очередь*, а не отправку и не прохождение 2FA.

| Ограничение | Привязка |
|---|---|
| `account_burst`, `account_day` | авторитетный ID аккаунта |
| `phone_burst`, `phone_day` | подтверждённый сервером E.164 |
| `ip_burst`, `ip_day` | проверенный исходный IP |
| `device_burst` | мобильная установка; **только дополнительный барьер** |
| `global_burst`, `global_day` | весь сервис V5 |
| `global_cost_day` | весь сервис V5, максимальная стоимость в младших денежных единицах |

Секрет для HMAC должен быть отдельным от JWT/V4 и единым для всех серверных процессов. Хранить **только** HMAC-ключи и счётчики; не логировать полные телефоны, IP, коды, device ID, токены или пароли.

**Числовые пороги квот нигде не предустановлены.** Слово `day` технически требует окно не менее 86400 секунд, `burst` — не менее 60 секунд. Дневной денежный бюджет — консервативное *резервирование стоимости по верхней оценке*, **не бухгалтерская фактическая сумма**; после ошибки отправки автоматически возвращать квоту нельзя.

## 3. Следующий обязательный интеграционный контракт — ещё НЕ реализован

`V5AtomicSmsOutboxPort::reserveAndQueue()` должен в **одной транзакции**:

1. Заблокировать реальный серверный челлендж по непрозрачному ID, установить доказательство пароля, состояние pending, совпадение user/device/platform/epoch и допустимый SMS-фактор. Не принимать клиентское `user_id`, `phone`, `cost` или якобы проверенное OTP. При изменении аккаунта или TOTP — запрет.
2. Повторно проверить под блокировкой текущую **верификацию номера**, его версию и телефонную привязку. При смене номера до фактической отправки worker должен повторно проверить версию или отменить outbox.
3. Для повторной отправки вызвать проверенную логику `ChallengeRules::canResendSms`: минимум **60 секунд** между отправками, не более **3** отправок на челлендж, TTL не более **300 секунд** и **никакого продления** исходного срока. Для первой отправки count должен быть 0. Проверять under lock — не только до запроса.
4. Проверить и увеличить **все 10** отсортированных квот вместе; переполнение *одной* квоты откатывает **все** изменения и не создаёт SMS-задачу.
5. В той же транзакции сохранить одну запись **зашифрованного** outbox, постоянный provider-idempotency key, ссылку на защищённый код/секрет и обновить счётчик отправок челленджа. Только после коммита разрешать попытку доставки.

Отправка SMS — за пределами транзакции. Нужны **фактически проверенный** SMS API и подтверждённая политика идемпотентности провайдера. Если неизвестно, доставлено ли SMS, а провайдер не гарантирует идемпотентность, не делать автоматическую вторую платную отправку: помечать исход как `unknown`. Нельзя выдавать JWT только на основании очереди или подтверждения провайдера.

Проверка шестизначного кода остаётся отдельным серверным одноразовым consume с максимумом **5 ошибок** и штатным V3C Bitrix TOTP для TOTP-ветки.

Пока **не реализованы**: реальный transaction/outbox, подтверждённый резолвер `b_user_phone_auth`, SMS pricing, провайдер и retry, проверка текущего MFA/epoch под блокировкой, V5 JWT и бонусный PIN. Не угадывать схему/состояние и не выполнять миграцию production.

## 4. Проверки и следующая точка продолжения
