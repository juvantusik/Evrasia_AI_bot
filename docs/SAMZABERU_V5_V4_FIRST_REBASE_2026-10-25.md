# СамЗаберу API V5 — V4-first: минимальная реализация вместо переписывания

Дата: 25.10.2026. Решение владельца: **взять год работающий V4 как исходный код, менять только авторизацию и legal/регистрацию**.

## Подтверждено на живом V4

- Реальный Bitrix API V4 находится в установленном docroot /home/site_evrasia/web/evrasia.spb.ru/public_html, а **не в GitHub-репозитории Evrasia_AI_bot**. GitHub содержит V5 feature код и документы, но не исходники установленных V4 router/controllers. Поэтому новая реализация V5 по частичным источникам стала расходиться с работающей корзиной.
- Реальный мобильный device_id **уже работает в V4** с 24.09.2026: sz_ + 64 lowercase hex, platform ios|android. Существующий TrustedDeviceMobileService приводит полный namespaced ID к core identity, общая система TrustedDeviceService и антифрод подтвердили production E2E. НЕ реализовывать эту систему повторно и НЕ ломать существующую регистрацию устройства.
- В V4 уже есть работающие маршруты/контроллеры корзины, оплаты при получении, оформления и получения заказов. Заказ передаётся из Bitrix через **уже существующий локальный механизм в колл-центр**, затем ресторан; никаких новых внешних очередей/серверов колл-центра в V5 не создавать.
- Сайт использует актуальные механизмы MFA, TOTP, email-first и trusted device, а также встроенные Bitrix UserConsent соглашения. Не создавать второй набор согласий или доверенных устройств.

## Конкретный план минимальной копии

1. Создать **приватный снимок точных установленных V4 PHP** (router, controllers, custom CartApiService, trusted-device services). Единственный скрипт в feature-ветке:
   site-integration/samzaberu-v5/deployment/snapshot-working-v4-for-v5-reuse.sh.
   Он работает только на root@evrasia, сверяет реальные baseline SHA V4 Cart/router, копирует source в /root/evrasia-v5-v4-source-snapshots, не выполняет source, не подключается к БД, не меняет веб-сайт. Снимок НЕ загружает в открытый GitHub и НЕ печатает файлы или токены.
2. **V5 бизнес-методы = копия В4:** сохранить те же схемы корзины, последовательности заказов, маршрутизацию из Bitrix в существующий локальный канал колл-центра, расчёт цен/скидок, доставку/самовывоз, profile/history, доступные клиенту поля. Не создавать новый D7 cart reader рядом с B_API_BASKET. Контракт существующего device_id оставить как есть.
3. **Только 3 группы отличий:** (A) вход и получение access/refresh через V5 сильную сессию с приоритетом доверенного устройства, серверной проверкой native Bitrix TOTP, email-first и разрешённым SMS fallback; (B) перед регистрацией выдавать актуальные legal документы и коды, включать выбранные agreement codes в заявку; (C) атомарно сохранять текущие согласия при создании пользователя через существующий Bitrix UserConsent. После этого продолжить существующие V4 бизнес-методы под проверенной V5 identity. **Не принимать V4 JWT как V5 JWT и не выдавать V4 сессию от непроверенной V5 identity.**
4. Провести сравнение реальных V4 и V5 endpoint requests/responses на контролируемом аккаунте, без синтетических пользователей/заказов и без пробного SMS/платежа. Включение V5 отдельно после согласования реального пилота; сохранить живой V4 без изменений.
5. Считать старый крупный feature-контур V5 **прототипом отдельных auth/legal компонентов**, а не новой базой для переписывания V4 корзины/заказов. Не переносить его новый checkout/поддельные cart adapters в production.

## Текущий честный статус

**V4 работает. V5 AUTH OFF.** Реальная V5-версия от работающего V4 ЕЩЁ НЕ СКЛОНИРОВАНА: исходников V4 нет в доступном GitHub, и инструмент снимка на сайте ЕЩЁ НЕ ЗАПУСКАЛСЯ. Этим решением прекращаем разработку параллельной самостоятельной бизнес-логики по mock-моделям.

После запуска единственного snapshot script нужно проверить фактическую копию V4 и заменить лишь auth/legal/consent точечно. Дальнейшее тестирование должно подтверждать реальный контракт V4, а не количество автономных mock-assertions.

Контракт разработчику следует уточнить: до выпуска V5 приложение продолжает использовать живой V4 для бизнес-методов и уже работающего device_id; новые V5 auth/legal методы проектируются отдельно. Не обещать V5 как доступный сейчас API.
