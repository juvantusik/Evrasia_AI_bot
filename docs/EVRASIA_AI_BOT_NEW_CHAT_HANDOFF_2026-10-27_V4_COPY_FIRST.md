## 2. Бизнес-правила: что нельзя менять

- **Гостевая корзина не требует авторизации:** просмотр, \`cart/id\`, добавление/удаление, \`plus\`/\`minus\`, \`clear\`, подарки, скидки и другие операции, доступные гостю в V4. Сохранять реально работающие \`cart_id\`/\`FUSER_ID\` и серверные проверки V4, не заменять алгоритм.
- \`plus\` и \`minus\` в V4 **относительные**, вызывают \`CartApiService::changeQuantity($cartItemId, +quantity/-quantity)\`. Ранее созданный V5 \`/cart/items/quantity\` с абсолютным количеством — **другая семантика**; **не использовать его вместо V4 plus/minus**.
- Отдельная V5-реализация \`CartApiServiceV5\` — точная копия V4 с переименованным PHP-классом, НЕ новая бизнес-модель. Не создавать ещё один сервис без реальной нужды.
- У неавторизованного человека сайт показывает набранную корзину и на этапе checkout имя/телефон; прежний UI предлагал SMS для авторизации. В целевом сценарии **не предлагать вход по SMS**: при необходимости дать просто вход/авторизацию. **Не предполагать самовольно**, что оформление заказа обязано быть публичным или обязательно требует JWT: фактическое условие V4 \`Cart::order()\`/checkout нужно внимательно сохранить и проверить; решение о спорных шагах запросить только если исходная V4-логика и указания владельца конфликтуют. Не выполнять реальное оформление заказа в production без явного разрешения.
- Новая авторизация нужна для **профиля, истории заказов, бонусной карты и кода списания бонусов (PIN)**. На этапе 1 не внедрять и не переписывать авторизацию; в этапе 2 интегрировать уже существующий V5 authentication/runtime в эти защищённые операции. Старый V4 JWT и SMS auth не переносить как V5 login.
- На этапе 3 подключить действующие юридические документы при регистрации и зафиксировать согласие. Существующие V5 legal endpoints и код не переписывать прежде времени; сначала оценить уже работающие функции. Работавший ранее сайт/его SMS fallback не трогать этим переносом приложения.
- V4 работающий и автономный в переходный период, не изменять оригинальные V4-файлы, исходный \`CartApiService\`, базу и связанные production-интеграции без необходимости. У пользователя нет задачи обслуживать две API вечно после будущего cutover.
- Никаких синтетических пользователей; пользователь подтвердил допустимость отдельного **реального гостевого FUSER** для теста корзины. Проверять реальное поведение, а не бесконечно только 400/415.

Следующим шагом исправить mapping, подключить их по фактическому V4 контракту, сделать реальные ограниченные гостевые HTTP проверки. Сразу выполнить минимальное исправление ошибочного предыдущего скрипта: \`/cart/clear\` должен вызывать **существующий скопированный \`V5\\Cart::removeAll()\`**, сохранить \`addGift/removeGift/applySale\`. Перенести недостающие гостевые V4 маршруты в V5 и проверить HTTP (с реальной пустой/изолированной гостевой корзиной, без пользователя и заказа); при ошибке автоматический rollback. Функции \`add/plus/minus/remove\` **уже доказаны реальным E2E**, повторять без оснований НЕ НАДО. Потом двигаться к \`/cart/order\` и остальным необходимым V4 бизнес-маршрутам, не создавать production заказ при самостоятельном smoke.

**Не путать две задачи:** на этапе 1 реализуются *ручки разработчика СамЗаберу*, а НЕ бесконечные проверки механизмов авторизации.

## 6. Изменение решений (БЫЛО → СТАЛО → ПРИЧИНА)

- **Было:** V5 private strong JWT транспорт + отдельные корзинные ports, \`GET /cart\`/ \`POST /cart/items/...\` требуют JWT, абсолютное количество.
- **Стало:** **V4-гостевая корзина 1:1**, оригинальные методы V4 (в копии V5), относительные \`plus/minus\`, работа без авторизации. Старые V5 JWT-обработчики не использовать как замену гостевых V4 операций.
- **Причина:** требования владельца, реальное поведение сайта/СамЗаберу, подтверждённый E2E.
- **Приоритет:** текущее production состояние > актуальный исходный код > документированные старые решения. Новое принятое 27.10 решение supersedes старые файлы 23–25.10 в вопросе очередности и guest cart.
