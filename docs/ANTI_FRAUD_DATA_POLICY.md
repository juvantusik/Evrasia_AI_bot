# Anti-Fraud — правила хранения и минимизации данных

## Назначение

Модуль Anti-Fraud хранит только те данные, которые нужны для объяснимого анализа устройств, посещений и связей между аккаунтами. Автоматическая блокировка пользователей в v1.7 не выполняется.

## RestIS и карты лояльности

- `CARD_NO` RestIS является техническим идентификатором карты лояльности, а не номером банковской карты.
- Raw `CARD_NO` хранится только в `anti_fraud_cards.card_number`, потому что он необходим для сервисного сопоставления с Bitrix.
- История посещений не дублирует raw `CARD_NO`: `anti_fraud_visits` использует внутренний `card_id`.
- `card_number` запрещено писать в application-логи, тексты ошибок, Telegram и публичные API-ответы Anti-Fraud.
- `anti_fraud_cards.card_number` имеет проверку формата и уникальный индекс.
- `anti_fraud_cards.bitrix_card_status_id` хранит raw ID статуса карты из Bitrix card-map; это не состояние RestIS и не должно интерпретироваться как RestIS enum.

### Текущий поток и адресная история

- `VIP_TODAY` используется как текущий инкрементальный поток посещений.
- Массовый исторический backfill по всей базе карт запрещён.
- `VIP_HISTORY` разрешается только для конкретного аккаунта после срабатывания Anti-Fraud risk gate.
- Для `VIP_HISTORY` выбираются только карты этого Bitrix `USER_ID`, у которых `anti_fraud_cards.is_active = true`.
- Неактивные карты не запрашиваются через `VIP_HISTORY` и не должны участвовать в Visit Behavior Risk.
- Целевое окно исторического анализа — последние 60 дней. RestIS может вернуть более глубокую историю, но события старше текущего lookback-окна не сохраняются этим enrichment-процессом.
- Повторный запрос истории ограничивается metadata-полями `history_loaded_from`, `history_loaded_until`, `history_loaded_at`; по умолчанию свежая 60-дневная выборка не запрашивается повторно чаще одного раза в 24 часа.
- Если ответ `VIP_HISTORY` достигает предельного `pagesize=10000`, enrichment останавливается без отметки успешного покрытия, потому что полнота истории не доказана.

## Bitrix-аккаунты и PII

- `phone_normalized`, `email_normalized` и `display_name` являются персональными данными и должны использоваться только внутри Anti-Fraud для анализа связанных/похожих аккаунтов и отображения уполномоченному сотруднику.
- Эти поля не должны попадать в Telegram-логи, технические ошибки, метрики и общие журналы приложения.
- `current_card_number` в аккаунте не хранится: связь аккаунта с одной или несколькими картами определяется через `anti_fraud_cards.bitrix_user_id`.
- До утверждения срока хранения PII отдельный production-коллектор Bitrix-аккаунтов не включается.

### Адресный Bitrix account-map

- `account-map` принимает только явный список Bitrix `USER_ID` и не предоставляет массовую выгрузку всей пользовательской базы.
- Collector формирует список только из аккаунтов, которые уже появились в Anti-Fraud через `anti_fraud_cards`, `anti_fraud_device_events` или ранее сохранённые `anti_fraud_accounts`.
- Один запрос ограничен 500 `USER_ID`; все запрошенные ID должны быть классифицированы как `records` или `unresolved`.
- Collector сохраняет только `bitrix_user_id`, нормализованные телефон/email, отображаемое имя, дату регистрации и `ACTIVE`.
- Значения телефона, email и имени запрещено включать в тексты ошибок collector/gateway и технические логи.
- Collector не удаляет локальный аккаунт при временном `unresolved`: источник может быть недоступен или пользователь может стать недоступен для чтения; такие случаи фиксируются только в sync-метриках.
- До утверждения retention PII этот collector разрешён для тестового контура, но не включается как production schedule.

## Trusted Device

- IP-адрес не хранится и не используется как фактор доверия или Anti-Fraud сигнал.
- `device_hash` используется как технический псевдоним устройства и должен соответствовать SHA-256 hex-формату `^[a-f0-9]{64}$`.
- `event_type`, `auth_method`, `client_type` и status текущей связи сохраняются как raw text. Ingestion не интерпретирует их как числовые enum и не присваивает им риск самостоятельно.
- Текущие user-device связи зеркалируются отдельно в `anti_fraud_device_links`, потому что поток `ev_device_auth_events` может быть неполным и не является достаточным источником текущего состояния связей.
- `anti_fraud_device_links` синхронизируется полным snapshot с reconcile по `source_link_id`; исчезнувшие из успешного snapshot связи удаляются локально.
- `anti_fraud_device_events` загружается инкрементально по монотонному source event ID. Повторный `source_event_id` с отличающимися core-полями считается ошибкой источника и не перезаписывается молча.
- Trusted Device export не передаёт телефон, email, имя пользователя, IP или trust token.
- До утверждения retention device telemetry collector разрешён для тестового контура, но не включается как production schedule.

## Ссылочная целостность

- `anti_fraud_visits.card_id` имеет FK на `anti_fraud_cards.id`, потому что RestIS collector всегда создаёт/обновляет master-карту до записи посещения.
- FK от Bitrix `user_id` к `anti_fraud_accounts` намеренно отсутствуют: источники синхронизируются независимо и могут приходить в разном порядке.

## Доступ

- Anti-Fraud данные не являются частью Phonebook или Telegram bot API.
- Доступ к будущему Anti-Fraud web UI должен предоставляться только явно разрешённым административным ролям.
- Service-token Bitrix хранится только в secret-файле и не сохраняется в БД.

## Retention

Сроки хранения посещений, device events и PII должны быть утверждены отдельно до включения соответствующих production-коллекторов. До утверждения запрещено добавлять автоматическое бессрочное накопление PII/device telemetry.
