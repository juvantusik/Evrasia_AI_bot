=== В ЧЕМ СЕЙЧАС ЗАДАЧА ===
Нужно дать разработчику «Сам Заберу»:
1. GET /api/v5/legal/registration-documents — актуальные offer / personal_data / optional marketing документы ДО регистрации, без JWT. Документы и коды нельзя хардкодить в приложении.
2. POST /api/v5/auth/signup — настоящая Bitrix-регистрация с полями phone, email, password, confirm_password, name (и допустимыми необязательными bday, sex), массивом agreements с текущими кодами; сервер повторно проверяет обязательные согласия, создает USER_ID, сохраняет реальные записи Bitrix UserConsent::addByContext, соблюдает необязательный marketing, отправляет подтверждение регистрации. Никаких JWT/траст-токенов при создании пользователя.
3. POST /api/v5/auth/signin — пароль с использованием существующего Bitrix и реальной MFA-политики. Действующий доверенный мобильный токен имеет ПРИОРИТЕТ над TOTP. Само приложение СОЗДАЕТ токен устройства, API НЕ ГЕНЕРИРУЕТ И НЕ ВОЗВРАЩАЕТ trust_token. Без валидного траста: активный TOTP -> TOTP challenge; без TOTP -> существующий проверенный email challenge и предусмотренный ручной SMS fallback.
4. POST /api/v5/auth/totp/verify, /auth/email/verify, /auth/sms/verify и общий /auth/challenge/verify — серверная проверка code + challenge_id + device_id + platform. Чужой тип фактора не принимает. 6-значный код, одноразовое погашение, без JWT до успешного MFA.
5. POST /api/v5/auth/challenge/resend и /auth/challenge/use-sms — повтор/ручной переход email->SMS, без автоматического ухудшения защиты при TOTP. SMS-код для входа НЕ равен бонусному PIN.
6. POST /api/v5/auth/refresh и /auth/logout — JWT/opaque rotating refresh и отзыв. POST /api/v5/loyalty/pin — только для подтвержденной сильной V5-сессии, прямой показ PIN, без лишнего SMS.
7. После этого профиль/корзина/заказы/оформление (в основном уже есть V4/V5 реализация), а не вместо перечисленного.
8. Выдать разработчику готовый контракт методов, поля JSON, responses, codes, сценарии доверенного устройства, TOTP, email, SMS и регистрации.
