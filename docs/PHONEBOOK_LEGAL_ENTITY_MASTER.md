# /phonebook — master-справочник юридических лиц

Дата решения: 13.09.2026
Статус: IN DEVELOPMENT
Jira: KAN-77
Ветка: `feature/v1.8-phonebook-legal-entities`

## Цель

Не создавать отдельную базу реквизитов и не дублировать юридические данные в разных модулях. Существующая PostgreSQL Evrasia AI Bot является единым master-data контуром `/phonebook`.

Существующая таблица `corporate_legal_entities` расширяется и становится source of truth по ЮЛ. Рестораны, корпоративные телефоны, лицевые счета и будущие документы должны ссылаться на ЮЛ через `legal_entity_id`.

## Главное правило source of truth

Если у записи есть `legal_entity_id`, отображаемые название ЮЛ, ИНН и генеральный директор читаются из `corporate_legal_entities`, а не из legacy-копий в таблицах телефонов/ресторанов.

Legacy-поля `legal_entity`, `inn`, `general_director` сохраняются только как fallback/backward compatibility для ещё не связанных записей и для безопасного переходного периода.

Следствие: изменение master-карточки ЮЛ должно автоматически отражаться во всех consumers `/phonebook` без ручного редактирования каждой связанной записи.

## UI

В `/phonebook` добавляется вкладка `Реквизиты` между `Рестораны и директора` и `МегаФон`.

Целевая последовательность:

`Рестораны и директора | Реквизиты | МегаФон | T2 | История`

Вкладка позволяет:

- искать и фильтровать ЮЛ;
- добавлять ЮЛ;
- редактировать ЮЛ;
- архивировать ЮЛ вместо физического удаления;
- видеть юридические реквизиты, адреса, генерального директора, банковские счета, операторские лицевые счета и связанные объекты.

Архивирование защищено guard: ЮЛ нельзя архивировать, пока на `legal_entity_id` ссылаются активные телефоны или рестораны. Сначала связи должны быть переназначены или закрыты. История при этом сохраняется.

## Идентичность ЮЛ

Название не является уникальным ключом.

Подтверждены два разных ЮЛ с одинаковым названием `Евразия-Триумф`:

- Новаторов 32 — ИНН `7817318001`, ОГРН `1097847304609`;
- Московский 222 — ИНН `7810591971`, ОГРН `1107847187524`.

Поэтому UI dropdown должен показывать как минимум `Название + ИНН`.

На этапе миграции существующих данных автоматическая связь по одному названию допускается только если название однозначно соответствует одному активному ЮЛ.

## Генеральные директора

Актуальный source of truth: файл `Списки дир-ов от 06.04.26.xlsx`, лист `Лист1`, колонка `ФИО директора (генерального)`.

Старые Word/XLS карточки реквизитов могут храниться как источник/история, но не должны автоматически переопределять более свежий источник.

## Адреса

Хранятся разные сущности:

1. `legal_address`, `actual_address`, `postal_address` ЮЛ — полные официальные значения без сокращения и смыслового исправления;
2. короткий адрес ресторана / display address — существующий компактный формат типа `Энгельса 21`, `Московский 222`, `Новаторов 32`.

Существующие короткие адреса ресторанов нельзя перезаписывать официальным длинным адресом ЮЛ.

Для новых ресторанов допустима автоматическая генерация короткого адреса из полного адреса, но результат должен быть редактируемым до сохранения.

## Модель данных

Используется одна БД и связанные таблицы:

- `corporate_legal_entities` — master ЮЛ;
- `corporate_legal_entity_bank_accounts` — один или несколько банковских счетов ЮЛ;
- `corporate_legal_entity_operator_accounts` — лицевые счета/договоры операторов;
- `corporate_phone_directory.legal_entity_id` — связь номера с master ЮЛ;
- `corporate_directory_restaurants.legal_entity_id` — связь ресторана с master ЮЛ.

На первом rollout legacy-поля `legal_entity`, `inn`, `account_number`, `general_director` сохраняются для обратной совместимости. Их нельзя удалять до полного перевода всех consumers и production-проверки.

## Валидация импортируемых реквизитов

Сомнительные значения не исправляются автоматически.

Для конфликтующих/подозрительных значений сохраняются:

- исходное значение;
- источник;
- `verification_status` (`VERIFIED`, `NEEDS_REVIEW`, `UNVERIFIED`);
- при необходимости комментарий/notes.

Нельзя объединять ЮЛ по ОМС, ПФ, email, адресу или похожему имени.

Банковские реквизиты, ОГРН/КПП, ОКВЭД и регистрационные номера из старых карточек с конфликтами должны пройти review перед установкой статуса VERIFIED.

## Формы phonebook

### Корпоративный номер

Поле `Юридическое лицо` должно стать searchable dropdown.

После выбора:

- название и ИНН берутся из master ЮЛ;
- ИНН не вводится вручную;
- лицевой счёт выбирается из связанных операторских счетов ЮЛ;
- если счетов несколько — пользователь выбирает нужный.

### Ресторан

Поле `Юридическое лицо` должно стать searchable dropdown.

После выбора:

- генеральный директор берётся из master ЮЛ;
- короткий адрес ресторана сохраняется отдельно и не заменяется полным `actual_address` ЮЛ.

## Документы v1.8

Шаблоны документов не должны содержать захардкоженные реквизиты.

Цепочка данных:

`phonebook context -> legal_entity_id -> master ЮЛ -> реквизиты/счета -> DOCX/PDF`

Это обеспечивает изменение реквизитов в одном месте и использование актуального значения во всех будущих документах.

## Миграции и CI

`0022_phonebook_legal_entity_master.sql` является первым schema rollout этого решения.

После добавления миграции обязательно одновременно:

- обновить `lib/db/drizzle/meta/_journal.json`;
- обновить hardcoded migration count в CI;
- добавить feature-specific schema smoke test.

DO NOT REPEAT: не оставлять CI с ожиданием старого количества миграций, как это произошло при rollout `0021`.

## Этапы rollout

1. Schema + API master ЮЛ, без destructive удаления legacy-полей.
2. Вкладка `Реквизиты` и CRUD/archive.
3. Dropdown ЮЛ в формах телефонов/ресторанов.
4. Безопасный backfill `legal_entity_id` и операторских лицевых счетов.
5. Master read semantics: связанные consumers читают актуальные ЮЛ/ИНН/гендиректора по `legal_entity_id`; legacy только fallback.
6. Archive guard для активных связей.
7. Подготовка canonical import из архива реквизитов и актуального файла директоров.
8. Review конфликтов пользователем.
9. Production import только подтверждённых данных.
10. Использование master ЮЛ генератором документов v1.8.
