# СамЗаберу API V5 — граница оформления и передачи в колл-центр

Дата: 2026-10-25. Статус: FEATURE ONLY / V5 AUTH OFF / PRODUCTION UNCHANGED.

## Решение владельца продукта (обязательное)

Правильный маршрут: СамЗаберу → самостоятельный API V5 → Bitrix Sale →
**действующий локальный канал передачи заказа в колл-центр** →
колл-центр → ресторан.

Зона работ V5 **заканчивается на принятии заказа существующим механизмом
Bitrix/передачи в колл-центр**. Не запрашивать доступы к серверам колл-центра,
не изучать их ПО, очереди, маршрутизацию по ресторанам или протоколы; не
создавать отдельную интеграцию V5 с рестораном или колл-центром.

Приём заказа существующим локальным каналом **не равен** подтверждению
доставки в колл-центр или ресторан. Эти внешние подтверждения не являются
частью MVP API V5.

## Верифицированные факты текущего Bitrix/V4

- `Cart::order()` создаёт заказ Bitrix Sale, назначает `IGNORE_RESTIS=Y`,
  вызывает `CartApiService::orderCreatedEvent()`.
- `COrder::orderSaveHook()` при `IGNORE_RESTIS=Y` пропускает обычную
  ветку отправки в RestIS. **Не** выключать флаг для обхода этой проверки
  без отдельного подтверждения существующего локального механизма.
- `CartApiService::orderCreatedEvent()` делает две операции `DELETE`
  для `B_API_BASKET WHERE FUSER_ID=?` и
  `BASKET_CUSTOM_GIFTS WHERE UF_FUSER_ID=?`.
  Оба условия точно подтверждены исходным кодом Bitrix.
  Этот метод не передаёт заказ в колл-центр.
- Оплата происходит **при получении в ресторане**. Нельзя требовать от
  приложения `payment`, инициировать шлюз или автоматически писать
  `PAYED=Y` / `STATUS_ID=F` при оформлении.

## Контракт V5 checkout (наша сторона)

1. Авторизовать V5 strong-session, заблокировать `b_user`, проверить epoch,
   собственный привязанный `FUSER_ID` и уникальный `request_id`.
2. Использовать актуальные серверные позиции/цены существующего
   `CartApiService`; с применением подтверждённых правил V4 сформировать
   native `Sale\Basket` и заказ D7. Платёжная запись — техническая,
   не оплаченная.
3. Проверить **существующее локальное принятие заказа Bitrix для передачи в
   колл-центр**. Проверка на локальных данных; не выполнять собственную
   сетевую отправку, не обращаться к серверам колл-центра и не создавать
   дополнительное сообщение в очередь. Положительный способ подтверждения
   пока НЕ ПРОВЕРЕН и НЕ ПОДКЛЮЧЁН.
4. Только после подтверждённого сохранения и локального принятия удалить
   старую API-корзину и связанные пользовательские подарки. После этого
   записать `saved` и подтверждённый заказ в уникальный V5-ledger, в одной
   подтверждённой физической транзакции Bitrix/V5. До принятия реального
   transaction-continuity proof никакого production checkout.
5. Повторный `request_id` возвращает неизменный результат. Никаких
   повторных D7 save, очисток, подтверждений или собственных внешних отправок.

В исходниках реализован интерфейс
`V5PickupLocalCallCenterHandoffProofPort`; реальной реализации в
production намеренно нет. Он подтверждает **только локальную границу**.
При невозможности доказать это — fail closed, а не ложный успех.

## Оставшиеся release gates (без доступа к колл-центру)

- Подтвердить действующее **локальное** условие передачи/принятия заказа в
  Bitrix; не инспектировать инфраструктуру колл-центра.
- **Подтверждено по реальному исходному коду**: удаление из
  `B_API_BASKET` по `FUSER_ID` и из `BASKET_CUSTOM_GIFTS` по
  `UF_FUSER_ID`. Обе операции имеют единственное условие WHERE;
  повторные проверки этих предикатов не нужны.
- Feature-only `V5BitrixNativePickupCartCleanup` реализует обе операции
  через строгий общий Bitrix SQL-адаптер, но **не подключён в production**.
  Перед записью требуются строгая native-транзакция и InnoDB для обеих
  таблиц, чтобы удаление могло откатиться вместе с созданием заказа.
- Проверить одним физическим транзакционным контуром V5 PDO bridge,
  Bitrix `Sale\Order::save()` и существующую `$DB`/очистку. Перед запуском
  очистки не допустить второй независимой транзакции.
- Только после подтверждения локальной передачи и транзакций — отдельное
  разрешение на ограниченный тест **реальным** пользователем и реальным
  заказом. Синтетические аккаунты не создавать.

## 2026-10-25: Реализация двух удалений и проверка CI

После реального `V5_POSTSAVE_SQL_SCOPE=PASS` реализована независимая V5-only очистка `B_API_BASKET WHERE FUSER_ID=?` и `BASKET_CUSTOM_GIFTS WHERE UF_FUSER_ID=?`, с параметром только из защищённой V5-сессии и заблокированного `b_sale_fuser`. Два запроса добавлены в **точный список разрешённых SQL**, а не в общий доступ ко всем DELETE. Операции выполняются через тот же native-адаптер Bitrix, что и V5 strong sessions. Новый метод `assertOwnedCheckoutTransactionContinuity()` запрещает выполнение cleanup на неподтверждённой или CLI/non-strict транзакции. Добавлен fail-closed контроль InnoDB для обеих таблиц. Никакого отдельного подключения PDO или отправки в колл-центр нет.

Автономный GitHub CI <https://github.com/juvantusik/Evrasia_AI_bot/actions/runs/40211875189> — SUCCESS. Проверено 146/146 source-only checkout assertions и 147 отдельных проверок fake Bitrix bridge, включая отказ неверным DELETE и откат обеих очисток на одном mock-native соединении. Это **не** доказывает атомарность живого `Sale\\Order::save()` и существующего `\$DB`: реальный E2E и production checkout остаются OFF. Схема request ledger в production не установлена. Локальный признак приёма заказа существующим каналом Bitrix→колл-центр также ещё требует подтверждения **на стороне Bitrix**, без обращения к серверам колл-центра.


## 2026-10-25: проверка реально сохранённого заказа

Исходники API V5 расширены интерфейсом `V5PickupSavedNativeOrderProofPort`
и строгой реализацией `V5BitrixNativePickupSavedOrderProof`. После нативного
`Sale\\Order::save()` и до проверки существующей локальной передачи в
колл-центр V5 проверяет непосредственно строку `b_sale_order` в той же
транзакции. Точная строка `SELECT ID, USER_ID, ACCOUNT_NUMBER, STATUS_ID,
PAYED, CANCELED FROM b_sale_order WHERE ID=? AND USER_ID=? LIMIT 2 FOR UPDATE`
допускается только через строгий FPM V5 bridge; диагностический CLI режим
не может выполнить её. Проверяются совпадение `ID`, `USER_ID`,
`ACCOUNT_NUMBER`, `STATUS_ID` (N/P), `PAYED=N` и `CANCELED=N`.
Любое отклонение блокирует подтверждение checkout и очистку корзины.

Это **не** подтверждение передачи заказа колл-центру. Порт подтверждения
локальной передачи по-прежнему требует самостоятельного доказательства
принятия существующим механизмом Bitrix. Реальный E2E с D7 и общей
транзакцией не проводился; API V5 AUTH OFF, production без изменений.
GitHub Actions `40213227241`: SUCCESS, 156 checkout + 186 bridge =
342/342 автономных проверок.
