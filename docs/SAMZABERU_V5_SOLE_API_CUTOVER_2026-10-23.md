# СамЗаберу: V5 — единственный целевой API, план прекращения V4

Дата принятия решения: **23 октября 2026**. Репозиторий `juvantusik/Evrasia_AI_bot`, ветка `feature/samzaberu-api-v5-auth-contract`.

## Зафиксированное новое решение пользователя

**Было:** V4 сохраняется полностью независимым и продолжает обслуживать действующие приложения; V5 развивается отдельными маршрутами, используя существующие Bitrix-бизнес-сервисы. Время прекращения V4 явно не было определено.

**Стало:** `https://evrasia.rest/api/v5` — **единственный целевой публичный API** для мобильного приложения «СамЗаберу» и соответствующих интеграций. V4 — **временный совместимый контур**, предназначенный лишь для обслуживания существующих клиентов до подтверждённого перехода. **После миграции всех потребителей V4 выводится из эксплуатации**, а не обслуживается параллельно бессрочно.

**Причина:** не дублировать инфраструктуру, интеграции и поддержку. Ускорить поставку рабочего V5, используя уже работающую бизнес-логику Bitrix/V4 и необходимые собственные гарантии V5 для MFA/JWT/SMS/блокировок.

**Не меняется:** не запускаем V4 HTTP-контроллеры из V5; не принимаем V4 JWT за сильную V5-сессию; не дублируем цены, RestIS/лояльность, расчёт корзины и услуги Bitrix; не создаём синтетических аккаунтов или mock API. Старый production не выключаем до безопасного cutover.

## Файлы реализации миграции

- `site-integration/samzaberu-v5/migration/v4-replacement-plan.json` — машинно-читаемый план с **33 известными направлениями**, сопоставленными V4/V5 операциями, незакрытыми пунктами, 62 ожидаемыми регистрациями и явно неизвестными потребителями. У статусов `feature_only` нет значения `production accepted`.
- `site-integration/samzaberu-v5/migration/V5V4ReplacementGate.php` — безопасная **только читающая** проверка плана, реальности V5-маршрутов и обязательных условий прекращения V4. Не обращается к Bitrix, не читает продакшен-логи, не отключает маршруты, не проводит миграцию БД.
- `site-integration/samzaberu-v5/tests/V5V4ReplacementGateTest.php` — offline-регрессия: неизвестный маршрут, ложная готовность, подмена основного домена, преждевременное выключение V4 и несовпадение source-count отвергаются.
- `.github/workflows/v5-offline-safety.yml` — проверка плана и безопасности решения при изменениях в этой feature-ветке.
- `docs/SAMZABERU_V5_V4_REAL_BUSINESS_ROUTE_PARITY_2026-10-23.md` — начальная реальная карта уже исследованных регистраций, без выдуманных callbacks.

**Проверка плана** (локально или CI, не на production):

```bash
php site-integration/samzaberu-v5/migration/V5V4ReplacementGate.php
php site-integration/samzaberu-v5/tests/V5V4ReplacementGateTest.php
```

Её `FINAL_STATUS=PASS` означает **проверенную структуру плана**, а **не разрешение отключить V4**. До подтверждённого cutover ожидаемо: `CURRENT_STATUS=V4_MUST_REMAIN_ACTIVE`, `V4_AUTOMATIC_SHUTDOWN=NO`. Даже кандидат после всех gate-ов подлежит отдельному операторскому одобрению и rollback-проверке.

## Порядок выполнения — реальная разработка, не второй архитектурный проект

1. **Функциональный паритет V5.** По уже полученному V4 роутеру заполнять карту всех 62 регистраций, отдельно классифицировать клиентские методы, фоновые задачи и внешние callback-и. Реализовать недостающие бизнес-ручки V5 непосредственными вызовами существующих Bitrix/RestIS services: корзина (read/add/remove/order), рестораны, заказы/история, профиль, лояльность/бонусы/PIN, QR и юридические согласия. Сначала методы, необходимые разработчику «СамЗаберу». Не переписывать работающий расчёт и не дублировать БД.
2. **Нативная безопасность только по обязательным границам.** Доработать проверенный парольный вход, TOTP либо доказанное trusted device/SMS на подтверждённый телефон, SMS anti-spam, native user status/epoch, безопасные JWT/refresh/revoke и PIN. Производственный вход V5 до этой приёмки остаётся OFF. Проверить отдельное подключение V5 cart на том же Bitrix connection, без доступа к guest/чужому FUSER и неопасное чтение legacy props.
3. **Фактическая приёмка API.** Native Bitrix read-only и разрешённые E2E, `evrasia.rest` HTTPS, мобильные DTO, права на чужие данные, регрессия старых V4 бизнес-результатов и исправление различий. Зафиксировать не только feature CI, но и реальные server/runtime проверки.
4. **Миграция потребителей.** Установить, кто реально использует V4: версии мобильных клиентов, интеграции партнёров, сервисные callback-и, background tasks. Обновить клиентов на V5, согласовать наблюдаемый период отсутствия V4-трафика, собрать обезличенные/агрегированные метрики использования (без секретов и PII). Пустой список известных клиентов **не означает** отсутствие пользователей.
5. **Контролируемый cutover.** Только после 100% классификации V4-регистраций, принятых V5 замен либо доказанного прекращения использования внутренних маршрутов, отсутствия V4-клиентов/трафика в согласованный период, готовности rollback, проверки production и отдельного решения оператора. Сначала возможность обратного переключения; затем выключение V4 HTTP точечно, наблюдение; только после этого удаление строго устаревших контроллеров.
6. **Сохранение общих сервисов.** Выключение `/api/v4` **не означает** удаление `CartApiService`, RestIS, Bitrix, Loyalty, TrustedDeviceService и других модулей, которыми продолжит пользоваться V5. Рефакторинг/удаление этих сервисов не входит в операцию cutover без отдельного dependency-аудита.

## Закреплённые запреты

Никакого `/api/v4`→`/api/v5` редиректа для POST/auth, V4→V5 обмена JWT, массового отзыва существующих V4-сессий до готовности клиентов, временного отключения V4 ради проверки, а также автоматического удаления V4-controller файлов. Не маркировать consumer inventory завершённым без подтверждения фактических обращений.

**Ближайший практический шаг:** продолжить функциональный V5 паритет на реальных бизнес-сервисах. Первый уже реализованный GET cart нужно довести до native Bitrix E2E и одинаковых сумм/владения корзиной, параллельно переносить остальные пользовательские методы по зафиксированной карте. Подготовленный план миграции не блокирует эту разработку; он блокирует лишь преждевременное прекращение V4.
