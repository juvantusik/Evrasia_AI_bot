1. Общие требования API
•  Базовый адрес API: https://evrasia.rest/api/v5; обязательный HTTPS. Пути и конечные слеши соблюдать буквально.
•  Мобильный device_id формируется приложением: sz_ + 64 символа lowercase hex; platform = ios или android.
•  trust_token приложение генерирует и хранит самостоятельно. Сервер не создаёт и не возвращает его; при повторном входе передавать вместе с тем же устройством.
•  Токены V5 не совместимы с JWT V4. Access/refresh выдаются только после подтверждённого trust или второго фактора.
•  Для защищённых операций по умолчанию использовать Authorization: Bearer <V5_JWT>. В отдельных POST access_token передаётся в JSON-теле; это обозначено в каталоге как «Да²». JWT V4 использовать нельзя.
•  Content-Type зависит от метода: большинство auth/legal и JSON /cart/items/* используют application/json; Mobile ID, notifications, restaurant-discount и /cart/order — application/x-www-form-urlencoded. Обязательно использовать формат из описания выбранной ручки.
•  Пароли, PIN, OTP, refresh/access и trust_token никогда не записывать в клиентские логи.
✓ Полностью проверено в рамках указанного пункта по зафиксированным результатам.
◐ Частичная проверка: отказ, отдельная ветка или код без успешного E2E. ✗ — заглушка. Символ «—» — вне интеграции. HTTP 200 сам по себе не подтверждает полную бизнес-операцию.
Как читать статусы
	Обозначение
	Значение для интеграции

	200 / 201 / 202
	Успешный HTTP-ответ соответствующей операции; наличие JWT уточняется в соседнем столбце.

	E2E с JWT
	Защищённый маршрут успешно вызван с действительным V5 access_token.

	Проверен отказ
	Сервер корректно вернул 400/401/405/422; успешное изменение данных не доказано.

	Маршрут / перенесён
	Путь существует, но успешный запрос или полное DTO не подтверждены.

	Не уточн.
	Требование к JWT/контракту неизвестно; не предполагать способ вызова.


2. Сводный каталог API V5
JWT: «Да» — требуется действительный access_token; «Нет» — access JWT не требуется; «Опционально» — ответ зависит от авторизации; «Гость» — гостевая ветка; «Не уточн.» — контракт не установлен. ¹ Для /auth/refresh используется refresh_token вместо access JWT. ² Access JWT передаётся в JSON-теле согласно контракту соответствующей операции.

3. Сервис и legal
GET  /health
✓ Проверка доступности  |  JWT: Нет  |  Проверка: 200 без JWT
Без авторизации. Использовать для проверки доступности API. В ответе присутствует состояние сервиса и признак auth_ready.
GET  /legal/registration-documents
✓ Документы до регистрации  |  JWT: Нет  |  Проверка: 200 без JWT
GET  /legal/consents
✓ Актуальный комплект согласий  |  JWT: Опционально  |  Проверка: 200 публично; 200 с JWT
Публичные методы возвращают массив documents с полями code, type, title, required, format, content и url. Для отображения юридических документов до регистрации использовать GET /legal/registration-documents. Согласия для существующего пользователя получать через GET /legal/consents.
	{
  "documents": [
    {
      "code": "<код>",
      "type": "<тип>",
      "title": "<название>",
      "required": true,
      "format": "<формат>",
      "content": "...",
      "url": "..."
    }
  ]
}


GET /legal/consents без JWT возвращает публичный каталог документов. При действительном V5 JWT каждый элемент documents содержит accepted (boolean), а ответ — acceptance_required (boolean): true, если не принято хотя бы одно обязательное согласие. Оба варианта GET возвращают HTTP 200; персональные поля проверены с действительным JWT.
POST  /legal/consents/validate
✓ Проверка набора принятых кодов  |  JWT: Нет  |  Проверка: 200 по действующим кодам; 400 по неверному коду
	{
  "agreements": [
    "<offer_code>",
    "<personal_data_code>"
  ]
}



	{
  "valid": true,
  "agreements": [
    "<offer_code>",
    "<personal_data_code>"
  ]
}


Перед signup проверьте актуальные согласия. Проверено: 200 для двух обязательных кодов и 400 для неверного кода. HTTP 409 при изменении документов предусмотрен контрактом, но отдельно не проверялся.
POST  /legal/consents/accept
◐ Принять актуальные согласия авторизованного пользователя  |  JWT: Да  |  Проверка: 200 с JWT; повторное принятие
POST /legal/consents/accept требует действительный V5 JWT и application/json. Передавайте agreements — массив актуальных кодов согласий из GET /legal/consents. При успешной обработке возвращаются success=true, acceptance_required=false и документы с обновлённым accepted. Повторная передача уже принятых кодов возвращает HTTP 200 и не создаёт новые согласия. Этот сценарий проверен с JWT и повторным GET; создание новой записи согласия не проверялось. При регистрации без JWT соглашения передаются в POST /auth/signup, а не в /legal/consents/accept.
	POST /api/v5/legal/consents/accept
Authorization: Bearer <V5_JWT>
Content-Type: application/json

{"agreements":["<offer_code>","<personal_data_code>"]}


Поля успешного ответа (внутри стандартной JSON-обёртки API):
	{
  "success": true,
  "acceptance_required": false,
  "documents": [
    {"code":"<offer_code>","accepted":true},
    {"code":"<personal_data_code>","accepted":true}
  ]
}

4. Регистрация, вход, MFA, токены
POST  /auth/signup
✓ Регистрация нового пользователя  |  JWT: Нет  |  Проверка: 201; email подтверждён в браузере
	{
  "registration": {
    "name": "Имя",
    "phone": "+79990000000",
    "email": "user@example.com",
    "password": "<пароль>",
    "confirm_password": "<пароль>"
  },
  "agreements": [
    "<offer_code>",
    "<personal_data_code>"
  ]
}


Необязательные поля: bday, sex. Ответ HTTP 201:
	{
  "status": "registered",
  "user_id": 123,
  "next_step": "email_confirmation"
}



	Регистрация не является входом. POST /auth/signup не выдаёт JWT. next_step=email_confirmation: подтверждение по ссылке из письма в браузере, затем вход в приложение. /auth/email/verify предназначен для OTP входа.


POST  /auth/signin
✓ Пароль, привязка устройства и запуск MFA  |  JWT: Нет  |  Проверка: 202 MFA и 200 trust; JWT выдаётся
	{
  "login": "user@example.com",
  "password": "<пароль>",
  "device_id": "sz_<64_hex>",
  "platform": "android",
  "trust_token": "<токен_устройства_если_есть>"
}


trust_token — необязательное поле, которое создаёт и хранит само приложение. При подтверждённом доверии сервер может вернуть HTTP 200 с access/refresh без нового OTP; иначе возвращает HTTP 202 и challenge. Сценарий 202 → MFA → 200 подтверждён.
	{
  "status": "challenge_required",
  "challenge_id": "<challenge_id>",
  "challenge_type": "totp",
  "expires_in": 300
}


Ответ при действующем доверии устройства, без второго фактора (HTTP 200):
	{
  "status": "authenticated",
  "access_token": "<jwt>",
  "refresh_token": "<refresh_token>"
}

Mobile ID — авторизация и получение JWT
Последовательность Mobile ID: POST /signin/mobileid → опрос POST /signin/mobileid/status → при NEED_SMS_CODE отправка POST /signin/mobileid/code → повторный /status до AUTH. При AUTH сервер выдаёт access_token и refresh_token; полученный V5 JWT используется для защищённых методов. Парольный POST /auth/signin для этого сценария не требуется.
POST  /signin/mobileid
✓ Запуск Mobile ID  |  JWT: Нет  |  Проверка: 200; запуск Mobile ID
Для запуска Mobile ID JWT не требуется. Content-Type: application/x-www-form-urlencoded. Передайте phone, созданный приложением device_id и platform (ios/android). В ответе HTTP 200 содержится id попытки (64 lowercase hex); используйте тот же id в следующих запросах. Внешняя JSON-обёртка определяется стандартом ApiResponse.

Content-Type: application/x-www-form-urlencoded

Статусы включают NEW, SENT, NEED_SMS_CODE, AUTH. При AUTH ответ содержит access_token и refresh_token (возможна вложенность полей в ApiResponse). 8. Заказы, детали и действия
GET  /orders
✓ История заказов  |  JWT: Да  |  Проверка: 200 с JWT; data/meta по коду
	{
  "data": [],
  "meta": {"total": 0, "page": 1}
}


Authorization: Bearer <V5_JWT>. Активный обработчик V5 передаёт в ApiResponse::data поля data (список) и meta (total, page). Элементы: no, human_no, amount, status, restaurant_address, order_date_time, pickup_time, prior_notification_enabled, rating, pay. Пример ниже — бизнес-данные, а не гарантия внешней JSON-обёртки.
GET  /orders/{id}
◐ Просмотр конкретного заказа  |  JWT: Да  |  Проверка: DTO по коду; успешный HTTP не проверен
id — номер заказа в URL. В V5 проверяется принадлежность пользователю. UserOrder::getOrder() формирует основные поля заказа и items: product_id, title, amount, qty, images (original, icon, desktop). Успешный HTTP 200 конкретного заказа не проверялся.
POST  /orders/detail
◐ Отдельный JSON-контракт получения заказа  |  JWT: Да²  |  Проверка: Ошибка 400; успех не проверен
	{
  "access_token": "<jwt>",
  "order_id": 123
}


По контракту ожидается HTTP 200 с полем order; если заказ отсутствует или не принадлежит пользователю, ожидается 404. Успешный ответ этого POST отдельно не подтверждён.

9. Системные операции и прочее
GET  /system_notifications
◐ Системные уведомления  |  JWT: Нет  |  Проверка: 200 без JWT
Системные уведомления доступны публично с HTTP 200. Это не пользовательские настройки SMS/email из /notifications. Формат отдельных уведомлений здесь не детализирован.
POST  /history/update
◐ Обновление истории бонусной карты  |  JWT: Да  |  Проверка: V5 bridge; код изучен, E2E не проверен
V5 использует V5HistoryBridge и существующий UserController::updateHistoryNew(). Операция обновляет историю бонусных карт; по коду передаёт в ApiResponse::data поля new_items, updated_at, html, cards. Успешный E2E не проводился; html и cards в отдельных ветках могут быть не заполнены.
10. Матрица ошибок и ограничения
	HTTP
	Значение

	200
	Успех защищённого или публичного чтения / подтверждённой операции.

	201
	Создание сущности (например, signup и ожидаемый успешный checkout).

	202
	Начат MFA challenge или запрошена операция доставки challenge.

	400
	Ошибка входных параметров/бизнес-валидации (для email, QR, карт и др.).

	401
	Требуется действительная V5-сессия/JWT или отказ во втором факторе.

	403
	Запрет доступа / отсутствие нужных условий (зависит от ручки).

	404
	Неизвестный путь или недоступный объект; после исправления rewrite V5 отдаёт JSON.

	405
	HTTP-метод не разрешён для данного пути.

	409
	Изменились версии юридических документов.

	422
	Ошибка валидации редактирования профиля; короткий password на реальном JWT.

	503
	Временная техническая недоступность; это не подтверждение бизнес-операции.



11. Правила интеграции
•  Для входа по email/паролю использовать signin → trust или challenge verify; для Mobile ID использовать три существующие ручки /signin/mobileid*. При AUTH сохранить V5 access/refresh. Не использовать V4 JWT.
•  На запросе оформления заказа после гостевой корзины обязательно инициировать авторизацию, сохранив cart_id; не считать guest корзину автоматически равной авторизованной.
•  Для профиля соблюдать точные пути и form-urlencoded; для JSON cart/items и auth/legal соблюдать JSON; три POST Mobile ID используют form-urlencoded.
•  При 401 обновить вход/сессию по принятому клиентскому сценарию; не пытаться обойти MFA и не посылать SMS самовольно.
•  Для экрана «Мои карты» использовать GET /loyalty/cards. Привязка — POST /loyalty/cards/add с card_number, card_type, address, region (form-urlencoded).
•  Для списания бонусов POST /loyalty/pin возвращает pin_code; для предъявления карты в выбранном ресторане POST /restaurant-discount с REST_ID возвращает checkin. Не заменять один другим.
•  Не считать непроверенные заказы и платёжные операции готовыми E2E. Trust validate/revoke: известны параметры и DTO по коду, успешный вызов не проверен. Подтверждение регистрационного email выполняется в браузере.
•  Не отправлять тестовые DELETE /profile, POST /cart/order, pay/cancel или изменение реальных пользовательских данных без отдельного безопасного сценария.
